# Member information design

ClanService reuses profile HTML for roster extraction using list-item `a.user[data-env][data-nick]` anchors in the verified `.clan_section .list.member .over_wrap > ul` container. Other player lists are excluded. Minimal supplied fixtures use a list-item fallback when that container is absent. Exact duplicate nickname/env pairs are removed, while distinct identifiers remain distinguishable. Parsed count must equal the profile count when known, detecting incomplete pagination or structure changes. The corrected public page supplied all 91 members.

MemberService resolves the requested nickname and asks PointBlankClient for deduplicated cached JSON. Encoded member attributes are decoded once, then encoded by URLSearchParams. Raw plus signs and base64 padding survive correctly. Zod validates the object, integer normalization rejects malformed comma groups and unsafe/negative numbers, and the model's icon comes exclusively from the roster.

The roster command calls the pure `sortMembersByRank` helper once before emoji preparation and pagination. `rankIconAsset` exposes the numeric asset suffix alongside its validated URL and emoji name. A stable descending numeric sort puts unavailable ranks last and returns a new array while retaining the original member objects. The same sorted array is reused for the initial reply, navigation and expiry; individual nickname lookup retains the original roster order. This implements asset-number ordering without inventing rank names or interpreting JSON Rank.

RankEmojiService prepares a map from the actual roster rank image URLs to Discord application emojis. RankEmojiClient lists the application's existing `pb_rank_<image number>` emojis and creates missing ones through the bot-token API. The same infrastructure handles clan badges under distinct `pb_clan_rank_<image number>` names, while roster preparation and sorting accept only member `rank_<number>.png` assets. RankIconClient accepts only official HTTPS `images/common/icon_ranking/rank_<number>.png` or `clan_<number>.png` assets, disables redirects, bounds responses to 256 KiB, validates PNG signatures and preserves the original bytes. These static image requests do not fetch clan/player endpoints. Serial creation and cached pending promises prevent duplicate uploads. Application emojis persist in Discord and are reused after process restarts; no local database or server emoji permission is needed. Failed creation remains retryable and logs only safe error metadata.

Roster EmbedBuilder renders `number. rank emoji **nickname**` using bounded escaped lines, with Previous/Next custom IDs containing a random session. An unavailable emoji falls back to a link to the original validated icon; absent icons are Rank N/A. Icon numbers and the technical footer are no longer shown. Emoji resolution happens once per roster invocation, and the same map is retained for page changes and expiry. A message-scoped button collector denies other users privately, acknowledges immediately and serializes edits. The global handler recognizes expired messages through an active-message set. End events remove the active ID and disable buttons.

Individual embeds display name, clan, EXP, kills, deaths, headshots and roster icon thumbnail. Commands defer all retrieval, then edit the response. Errors are centrally handled without exposing technical payloads.
