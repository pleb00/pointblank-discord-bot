# Member information design

ClanService reuses profile HTML for roster extraction using list-item `a.user[data-env][data-nick]` anchors in the verified `.clan_section .list.member .over_wrap > ul` container. Other player lists are excluded. Minimal supplied fixtures use a list-item fallback when that container is absent. Exact duplicate nickname/env pairs are removed, while distinct identifiers remain distinguishable. Parsed count must equal the profile count when known, detecting incomplete pagination or structure changes. The corrected public page supplied all 91 members.

MemberService asks PointBlankClient for deduplicated cached ranking HTML with fixed `termtype=3` and the complete nickname as `keyword`, encoded through URLSearchParams. It does not depend on ClanService. The pure player parser scopes identities to `.nrank_table > .r_tr .r_td.name > a[data-env][data-nick]`, preserving attributes exactly. Required table/identity changes fail; the verified `.nodata_n` message with no rows produces an empty result. Exact nickname matches win, a unique folded match among returned rows is accepted, and partial or ambiguous matches never select a player.

PlayerSearchResult stores ranking position from `.r_td.win`, search EXP from `.r_td.exp > .txt`, and the rank name from `.r_td.rank > .txt` after removing `.rank_img`. The original row image must validate as an official member rank asset. Missing or malformed optional fields remain null; integer normalization rejects malformed comma groups and unsafe/negative numbers. After selecting the nickname, MemberService calls getMemberDetail with only the matched encoded identifier. The detail client decodes it once and uses URLSearchParams with div=1; raw plus signs and base64 padding survive correctly.

normalizeMemberDetail maps JSON Exp/Kill/Death/Headshot and ClanName/ClanTroops/ClanExpRank. normalizePlayerDetail adds the HTML game ranking/rank name/icon, calculates kills/deaths and headshots/kills × 100 without rounding internally, and returns a PlayerDetail without the identifier. Missing inputs and zero denominators yield null. JSON Rank is ignored; detail Exp is authoritative for Total EXP rather than falling back to search EXP. Entirely unusable counters fail clearly; partial counter warnings contain only field names. Detail failures retain the existing access, timeout and rate-limit errors and never become a successful partial profile.

The roster command calls the pure `sortMembersByRank` helper once before emoji preparation and pagination. `rankIconAsset` exposes the numeric asset suffix alongside its validated URL and emoji name. A stable descending numeric sort puts unavailable ranks last and returns a new array while retaining the original member objects. The same sorted array is reused for the initial reply, navigation and expiry; individual nickname lookup uses its separate ranking search. This implements asset-number ordering without inventing rank names or interpreting JSON Rank.

RankEmojiService prepares a map from the actual roster rank image URLs to Discord application emojis. RankEmojiClient lists the application's existing `pb_rank_<image number>` emojis and creates missing ones through the bot-token API. The same infrastructure handles clan badges under distinct `pb_clan_rank_<image number>` names, while roster preparation and sorting accept only member `rank_<number>.png` assets. RankIconClient accepts only official HTTPS `images/common/icon_ranking/rank_<number>.png` or `clan_<number>.png` assets, disables redirects, bounds responses to 256 KiB, validates PNG signatures and preserves the original bytes. These static image requests do not fetch clan/player endpoints. Serial creation and cached pending promises prevent duplicate uploads. Application emojis persist in Discord and are reused after process restarts; no local database or server emoji permission is needed. Failed creation remains retryable and logs only safe error metadata.

Roster EmbedBuilder renders `number. rank emoji **nickname**` using bounded escaped lines, with Previous/Next custom IDs containing a random session. An unavailable emoji falls back to a link to the original validated icon; absent icons are Rank N/A. Icon numbers and the technical footer are no longer shown. Emoji resolution happens once per roster invocation, and the same map is retained for page changes and expiry. A message-scoped button collector denies other users privately, acknowledges immediately and serializes edits. The global handler recognizes expired messages through an active-message set. End events remove the active ID and disable buttons.

Separate command modules own each workflow: `/info-clan` accepts an optional configured clan and shows its profile; `/info-member` accepts only an optional configured clan and handles roster pagination; `/info-player` accepts only a required nickname and shows the combined player details. The embed uses the nickname as its title and the original rank thumbnail, then two full-width Player Info / Clan Info fields. Player Info has profile, combat and headshot groups separated by blank lines; Clan Info has name, members and ranking. Integer counters use thousands separators and ratios use two decimals. Upstream names are escaped and limited so every field stays within 1024 characters. A player search neither filters by clan nor substitutes the configured clan as player data. Commands defer all retrieval, then edit the response. Errors are centrally handled without exposing technical payloads. Explicit registration deploys all three command definitions, removes the old member nickname option and keeps roster expiry messages referring to `/info-member`.
